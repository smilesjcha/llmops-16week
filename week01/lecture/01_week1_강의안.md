# Week 01 — 호출 너머의 LLM 운영

## 강의 정의

- 핵심 문장: 수강생은 대규모 언어 모델(Large Language Model, LLM)을 한 번 호출하는 사람에서 응답을 기록·평가·재현·개선하는 운영자로 전환한다.
- 기본 운영: 180분 워크숍(개념·대화 120분, 환경·실습 47분, 휴식 20분, 회고 3분).
- 압축 운영: 100분 핵심 경로.
- 실습 서비스: TRACE/01, 필수 결정론적 데모 제공자와 선택 Ollama 제공자.
- 완료 조건: 실행 가능한 서비스, 같은 입력의 실행 추적(trace) 2건 이상, 단일 변수 비교, 다음 개선 판단 2문장.

## 과목 운영자 소개

> 차성재 | 무신사 Core AI PM × 아주대 AI대학원 겸임교수
> Artificial Intelligence(AI) · Product Manager(PM)

- 정형 데이터·컴퓨터 비전·생성형 인공지능을 제품 문제, 평가 기준, 운영 증거로 연결한 실무·교육 경험.
- 공개 자료에서는 승인된 역할과 공개 경력만 사용하며 내부 프로젝트, 내부 지표, 연락처는 제외.
- 수업의 초점은 도구 나열이 아니라 문제 정의에서 운영 판정까지 이어지는 서비스 개선의 전체 흐름.

## 이번 학기 프로젝트 운영

- 중간고사: 기말 프로젝트를 실제로 진행하기 위한 기획서 문서.
- 누적 방식: 매주 만든 문제 정의, 실행 추적, 평가 기준, 버전 기록을 기획서와 포트폴리오에 연결.
- 질의응답 방식: 교수 질문 → 학생 결정 → 근거 보강 → 수정 이력 → 다음 질문의 반복.
- 중간 기획서의 핵심: 문제·사용자, 대표 입력, 성공·금지 조건, 평가 방법, 시스템 경계, 운영 위험, 실행 계획, 포트폴리오 증거.
- 기말 프로젝트의 핵심: 중간 기획서의 주장과 가설을 서비스, 실행 증거, 비교 평가, 개선 기록으로 검증.

## 이 과목의 라이프사이클 기준

이 강의의 5단계는 업계의 유일한 표준이 아니다. 2025년 2학기 자료의 구조를 16주 산출물과 운영 증거에 맞춰 재정리한 대규모 언어 모델 서비스 개선용 교육 프레임이다.

1. 기획·데이터
2. 프롬프트·맥락
3. 실행·배포
4. 평가·관찰
5. 개선·버전

훈련(Training), 평가(Evaluation), 배포(Deployment), 유지관리(Maintenance), 폐기(Retirement)는 모델 또는 전체 인공지능 시스템의 생성부터 종료까지를 설명하는 또 다른 관점이다. 이 과목의 프레임과 경쟁하는 오답이 아니라 관리 대상과 목적이 다른 분류다. 미세조정은 여러 개선 수단 중 하나이며, 폐기는 서비스 개선 5단계와 별도로 판단하는 운영 경계다.

이 과목은 기준(성공·금지 조건), 맥락(사용자·업무·데이터·권한), 버전(변경 대상·이유), 평가(같은 입력·판단 축)를 모든 개선 주장의 공통 좌표계로 사용한다.

## 용어 표기 원칙

- 축약어를 처음 제시할 때 한글 의미와 영문 풀네임을 함께 쓴다.
- 대규모 언어 모델 운영(Large Language Model Operations, LLMOps), 기계학습 운영(Machine Learning Operations, MLOps), 개발·운영(Development and Operations, DevOps)을 구분한다.
- 검색 증강 생성(Retrieval-Augmented Generation, RAG), 지도 미세조정(Supervised Fine-Tuning, SFT), 인간 피드백 기반 강화학습(Reinforcement Learning from Human Feedback, RLHF), 직접 선호 최적화(Direct Preference Optimization, DPO), 저랭크 적응(Low-Rank Adaptation, LoRA)을 처음 노출할 때 풀어 쓴다.
- 응용 프로그래밍 인터페이스(Application Programming Interface, API), 그래픽 처리 장치(Graphics Processing Unit, GPU), 개인식별정보(Personally Identifiable Information, PII)도 같은 원칙을 적용한다.

## 학습성과

1. 인공지능, 딥러닝, 트랜스포머(Transformer), 대규모 언어 모델의 전환을 병목 이동의 관점으로 설명한다.
2. 모델 능력과 서비스 신뢰성의 차이를 사용자·맥락·성공·경계 계약으로 설명한다.
3. 프롬프트, 검색 증강 생성, 도구 호출, 모델 라우팅, 지도 미세조정, 선호 학습, 저랭크 적응의 개입면과 비용·가역성을 구분한다.
4. 개발·운영, 기계학습 운영, 대규모 언어 모델 운영에서 관리 자산이 어떻게 누적되는지 설명한다.
5. 품질·지연시간·비용·안전성·재현성을 공통 판단 축으로 사용한다.
6. 서비스 개선 폐루프를 자신의 기말 프로젝트 기획서와 16주 산출물에 매핑한다.
7. Python 3.11.14 환경에서 응용 프로그래밍 인터페이스를 실행하고 최소 실행 추적 스키마를 확인한다.
8. 한 번에 변수 하나만 바꾼 기준선·변형 비교로 다음 버전 가설을 제시한다.

- 화면: 규칙 → 학습 → 규모 확장 → 생성 → 운영의 시간선.

- 화면: 첫 토큰부터 마지막 토큰까지 순차 상태 전달.

- 화면: 입력 토큰 행, 현재 해석 위치, 질의(Query)·키(Key)·값(Value) 역할 카드를 순서대로 배치한 독해 흐름.
- 핵심: 자기 주의(Self-Attention)는 현재 위치가 다른 위치에서 참고할 관계와 전달할 정보를 계산하는 구조.

- 화면: 토큰 관계의 설명용 열지도.

- 화면: 토큰 → 질의·키·값(Query, Key, Value) → 주의 → 순방향 신경망(Feed-Forward Network) → 맥락.
- 핵심: 학습 시 위치 병렬화와 장거리 관계 처리, 추론 시 자기회귀 반복의 구분.

- 화면: 생성 능력과 사실성·최신성·권한·지연시간·비용·안전성의 2분할.

- 화면: 질의 → 검색 → 근거 → 맥락 → 답변.

#### 50. 버전 조합의 실행 단위
- 화면: 실행 추적 식별자, 프롬프트 버전, 제공자·모델, 업무·설정, 상태·지연시간, 콘텐츠 지문, 출력, 토큰, 시각.

- 화면: 품질·지연시간·비용·안전성·재현성.

### F. 서비스 개선 폐루프 — 58–65

#### 58. 서비스 개선 폐루프의 전체 구조
- 화면: 5단계 순환, 계속·교체·종료 경계, 다섯 판단 축.
- 핵심: 평가·관찰이 다음 기획과 변경 가설로 돌아가며 특정 마지막 노드는 없다.

#### 59. 1단계 / 기획·데이터의 성공 계약
- 화면: 사용자 결정, 대표 입력, 성공·금지 조건, 평가셋, 개인정보·라이선스·보존 경계의 캔버스.
- 핵심: 성공 기준은 기획 단계에서 정의하고 평가 단계에서 측정.

#### 60. 2단계 / 프롬프트·맥락의 버전 계약
- 화면: 프롬프트 식별자·버전·책임자, 입력·출력 스키마, 예시, 검색·도구 맥락 참조.
- 핵심: 읽기 좋은 문장보다 고정 평가셋에서 비교 가능한 버전 계약.

#### 61. 3단계 / 실행·배포의 실패 경로
- 화면: 정상·시간 초과·재시도·대체 경로를 분리한 실패 레인.
- 핵심: 정상선만 있는 구조도는 데모 문서이며 실패 경로까지 있어야 운영 문서가 된다.

#### 62. 4단계 / 평가·관찰의 분포 기준
- 화면: 품질 성공·실패, 50·95백분위 지연시간, 오류율, 토큰·비용·안전 신호의 관찰 보드.
- 핵심: 오프라인 평가와 운영 관찰을 구분하고 같은 버전과 실행 추적에 연결.

#### 63. 5단계 / 개선·버전의 판정 기록
- 화면: 버전 1 → 가설 → 단일 변경 → 판정 → 버전 2 출시 또는 되돌리기의 기록.
- 핵심: 실패한 실험도 다음 선택지를 줄이면 유효한 포트폴리오 증거.

#### 64. 버전 변경의 최소 기록
- 화면: 버전, 가설, 변경, 실행 추적, 판정의 변경 기록 예시.
- 핵심: 번호보다 가설 → 변경 → 증거 → 판정의 연결이 중요.

## 현업 관점의 교수자 노트

- 훈련·평가·배포·유지관리·폐기를 틀린 답으로 처리하지 않는다. 먼저 관리 대상, 목적, 순환 여부, 종료 경계를 확인한다.
- 이 과목의 5단계를 업계의 단일 표준이라고 말하지 않는다. 16주 산출물을 잇는 서비스 개선용 교육 프레임으로 범위를 고정한다.
- 중간고사는 기말 프로젝트의 기획서다. 교수는 정답을 대신 정하지 않고 질문으로 설계의 빈칸과 근거 부족을 드러낸다.
- 학생은 교수 질문을 그대로 답안에 붙이지 않고 자신의 결정, 근거, 변경 내용을 수정 이력으로 남긴다.
- 설치에서 막히면 짝 프로그래밍 또는 결정론적 데모 제공자로 전환해 환경 복구가 유일한 성과가 되지 않게 한다.
- 최신·가장 큰 모델보다 같은 입력·버전·평가 기준을 고정하는 습관을 먼저 만든다.
- 평균 지연시간만 제시하면 50·95백분위와 원시 실행 추적을 함께 묻고, 결과만 제시하면 프롬프트·모델·설정 버전을 묻는다.
- 실제 고객 원문을 사용하지 않는다. 콘텐츠 지문은 익명화가 아니라 동일 입력 비교용 식별자다.
- 토큰 수는 교육용 추정치임을 명시하고 실제 과금 판단에는 모델 토크나이저 또는 제공자 사용량을 사용한다.
- 결과가 좋아졌다는 주장에는 대표 실패, 다른 판단 축의 회귀, 다음 변경 가설을 함께 요구한다.
- 파랑은 현재 초점, 변경 변수, 실제 운영 증거처럼 의미가 있을 때만 사용한다. 마지막 단계나 마지막 장이라는 이유만으로 강조하지 않는다.
