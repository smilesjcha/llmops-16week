실행 전 준비

1주차에서 준비한 Python 3.11.14, 공통 가상환경 .venv와 requirements.txt를 그대로 사용합니다. 2주차 추가 패키지나 유료 API 키는 필요하지 않습니다. API는 Application Programming Interface, 프로그램 간 기능 호출 인터페이스입니다.

Visual Studio Code(VS Code)에서 수업의 llmops-16week 폴더를 엽니다. 터미널의 현재 위치에 requirements.txt와 week02 폴더가 보여야 합니다. 코드를 아직 받지 않았다면 공개 강의 저장소의 Code → Download ZIP으로 내려받아 압축을 풉니다.

기존 환경이 준비되어 있다면 아래 서버 실행 명령만 사용합니다. 처음 환경을 만드는 경우에는 1주차에 준비한 uv(Python 환경·패키지 관리 도구)가 설치되어 있어야 합니다. uv 명령이 없다면 설치부터 교수자에게 확인합니다. 기존 .venv를 불필요하게 다시 만들지 않습니다.

macOS / Linux

처음 환경을 만들 때만 실행

uv python install 3.11.14
uv venv --python 3.11.14 .venv
uv pip install --python .venv/bin/python -r requirements.txt
uv pip check --python .venv/bin/python

서버 실행

.venv/bin/python -m uvicorn prompt02.main:app --app-dir week02/lab --host 127.0.0.1 --port 8002

Windows PowerShell

처음 환경을 만들 때만 실행

uv python install 3.11.14
uv venv --python 3.11.14 .venv
uv pip install --python .\.venv\Scripts\python.exe -r requirements.txt
uv pip check --python .\.venv\Scripts\python.exe

서버 실행

.\.venv\Scripts\python.exe -m uvicorn prompt02.main:app --app-dir week02/lab --host 127.0.0.1 --port 8002

터미널에 실행 주소가 표시되면 브라우저에서 http://127.0.0.1:8002를 엽니다. 서버 터미널은 켜 둡니다. 추가 명령은 새 터미널에서 실행합니다. Windows에서는 macOS/Linux용 VS Code 자동 작업 대신 위 PowerShell 명령을 사용합니다.

실제 환경 실행 검증은 macOS에서 진행했습니다. Linux·Windows의 실제 실행은 검증하지 않았습니다. 노트북을 사용하는 경우에도 인터프리터·커널은 같은 .venv를 선택합니다.

  1. Demo에서 24건 비교실행 모드 Demo와 합성 문의 T01–T08 8건을 확인하고 3개 버전 비교 실행을 누릅니다. v1·v2·v3에 같은 문의가 전달됩니다.
  2. 프롬프트와 실패 사례 확인세 버전의 규칙·출력 형식·예시를 읽습니다. 실패 결과를 열어 문의 원문, 기대 결과, 실제 응답과 검사 이유를 비교합니다. 예: T01/v1은 형식 오류, T03/v2는 분류 오류, T08/v2는 미확정 환불 약속입니다.
  3. 선택 또는 보류 이유 기록다음에 검증할 후보 버전을 선택하고 근거를 15자 이상 입력한 뒤 결정 기록 추가를 누릅니다. 아직 채택하기 어렵다면 보류 이유를 적어도 됩니다.
  4. JSON 보고서 저장JSON 보고서 내보내기를 누릅니다. 내려받은 파일을 VS Code에서 열어 24건 비교 결과와 선택 근거가 함께 저장되었는지 확인합니다.
  5. 분석 PDF 작성과 제출다음 네 가지 질문에 답한 문서를 PDF로 저장합니다. JSON과 PDF 두 파일이 열리는지 확인하고, 위의 소속별 경로로 제출합니다.

서버를 종료하기 전에 JSON을 먼저 저장합니다. 서버를 종료·재시작하면 실험 기록이 사라집니다. 저장을 마치면 서버 터미널에서 Ctrl+C로 종료합니다.

실행이 안 될 때

  • No module named prompt02: 저장소 루트에서 실행했는지, 명령에 --app-dir week02/lab이 포함되어 있는지 확인합니다.
  • 8002 포트 사용 중: 이미 실행한 실습 서버가 있다면 그 화면을 사용합니다. 다른 프로그램을 임의로 종료하지 않습니다.
  • JSON 형식 실패: 서버 고장이 아니라 모델 응답의 형식 문제일 수 있습니다. 원문을 보고 실패 이유를 분석합니다.
  • 저장한 기록이 사라짐: 서버를 다시 시작하면 기록이 초기화됩니다. Demo 비교를 다시 실행하고 선택 근거를 입력한 뒤 즉시 내보냅니다.
04

분석 문서의 네 가지 질문

어떤 실패가 있었나요?

  • 문의 번호와 프롬프트 버전을 적습니다. 예: T03 / v2.
  • 기대 결과와 실제 응답에서 다른 부분을 짚습니다.
  • 형식 오류인지, 분류·업무 규칙 판단 오류인지 구분합니다.
  • 자동 검사 결과만 옮기지 말고, 사람이 읽었을 때 왜 문제가 되는지 설명합니다.

어떤 버전을 선택하고 싶나요?

  • v1·v2·v3의 지시·출력 형식·예시 중 무엇이 다른지 비교합니다.
  • 지금 선택할 후보와 이유를 적습니다. 보류 이유를 설명해도 됩니다.
  • 이 결과만으로 실제 서비스에 적용해도 되는지, 무엇을 더 확인해야 하는지 적습니다.

다음에는 어떤 문의로 확인할 건가요?

  • 기존 8건과 다른 합성 문의 1건을 직접 만듭니다. 실제 고객의 문의를 가져오지 않습니다.
  • 기대하는 category, priority, needs_review와 판단 이유를 적습니다.
  • 어떤 모호함이나 실패 가능성을 확인하려는 사례인지 설명합니다.
  • 새 사례를 실행하지 않았다면 “검증 계획 · 미실행”으로 표시합니다. 실행 결과를 만들어 쓰지 않습니다.
category
담당 업무 분류: delivery 배송 / refund 환불 / exchange 교환 / account 계정 / other 기타
priority
처리 우선순위: normal 일반 / urgent 긴급
needs_review
추가적인 사람 검토 표시: true 필요 / false 별도 표시 없음. 답변 초안은 실제 고객에게 자동 전송되지 않습니다.

기대값은 교육용 합성 서비스의 업무 기준입니다. 모든 회사에 공통인 정책은 아닙니다. 결과의 reply는 상담 담당자가 읽을 5–160자의 한국어 답변 초안입니다.

교수에게 무엇을 묻고 싶나요?

  • 실험·평가·업무 규칙 중 이해가 어렵거나 의견을 듣고 싶은 질문 1개를 적습니다.
예: “교환과 환불이 함께 있는 문의를 첫 요청으로 분류하는 기준이 실제 서비스에서도 적절할까요?”
05

Demo와 실제 모델의 구분

필수 과제는 Demo만으로 완료할 수 있습니다. 모델 설치나 유료 호출이 필요하지 않습니다. 높은 성공률보다 같은 조건의 비교, 실패 해석과 선택 근거를 설명하는 데 집중합니다.

  • Demo는 수업용 고정 응답을 재생합니다. 버전별 결과 차이는 정해진 예시이며 실제 대규모 언어 모델(Large Language Model, LLM)의 성능 측정값이 아닙니다.
  • 프롬프트 파일을 수정해도 Demo 응답은 바뀌지 않습니다. 변경된 지시와 확인하려는 효과는 개선안으로 적고, 개선 효과를 검증했다고 쓰지 않습니다.
  • Ollama로 추가 실험했다면 Demo와 구분하고, 모델명·실행 조건·실제 성공·실패·미실행 건수를 함께 기록합니다.
  • 설치 실패나 장비 성능 때문에 Ollama를 사용하지 못해도 필수 과제를 제출할 수 있습니다.

선택 실습 · Ollama

Ollama는 선택 실습입니다. 진행하려면 설치된 Ollama 앱을 켜고, 별도 터미널로 모델을 확인·준비합니다. 처음 받는 모델은 다운로드와 로딩 시간이 필요합니다.

ollama list
ollama pull qwen3:4b-instruct
ollama run qwen3:4b-instruct "한국어로 준비 완료라고만 답하세요."

모델이 한 번 응답하면 실습 화면에서 Ollama를 선택하고 기본 선택된 T01 한 건으로 시작합니다. 이번 코드의 기본 설정은 think:false, temperature:0, seed:42, num_ctx:4096, num_predict:384입니다. 각각 Thinking 비활성화, 생성 무작위성 조절, 난수 시드, 문맥 길이, 생성 토큰 상한을 뜻합니다. 같은 시드를 사용해도 장비·모델 버전에 따른 결과 차이가 생길 수 있습니다.

연결 오류나 시간 초과가 나면 오류를 기록하고 Demo 과제를 먼저 마칩니다. 앱은 자동으로 Demo로 전환하지 않습니다. 다른 실행 모드의 결과를 실제 모델 결과로 합쳐 보고하지 않습니다.

제출 전 확인

  • JSON에 8개 문의 × 3개 버전의 비교 결과와 선택 근거가 들어 있습니다.
  • 실패 1건의 기대 결과와 실제 응답을 비교했습니다.
  • 선택 이유와 아직 확인하지 못한 한계를 구분했습니다.
  • 새 합성 문의 1건, 기대 기준, 교수에게 묻고 싶은 질문을 적었습니다.
  • Demo와 실제 모델 결과, 실행 결과와 검증 계획을 구분했습니다.
  • JSON과 PDF 두 파일을 직접 열어 확인했습니다.
  • 실제 고객 문의·연락처·학생 개인정보·API 키·접속 토큰을 넣지 않았습니다.

본인 식별 정보는 소속별 제출 안내에 따라 LMS·이메일에 기재합니다. 실험 데이터와 공개 저장소에는 본인이나 다른 사람의 개인정보를 넣지 않습니다.
