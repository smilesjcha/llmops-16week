현재 운영은 9월 11일 2주차, 9월 25일과 10월 9일 녹화영상 대체, 10월 23일 기획서 온라인 제출·평가, 12월 18일 실시간 온라인 프로젝트 발표를 따른다. 현재 주차만 색상으로 구분하며 특정 학교를 수강 대상으로 한정하는 표현은 운영 장표와 실습 화면에 사용하지 않는다.

## 노트북별 개선 근거

### 01 · 기본 프롬프트

원본은 문제 정의, 역할, 어조, 형식, 구분자, 길이, 공통 문맥과 추가 질문을 각각 실행한다. 이 설계 요소를 유지하되 다음을 수정했다.

- `OpenAI()`의 초기화와 유료 호출이 기초 경로에 섞여 있었다. 새 필수 경로는 계정·키·모델 다운로드 없이 demo를 실행한다.
- 모델 호출 오류를 `"Error: ..."` 응답 문자열로 반환했다. 새 실습은 실행 오류와 생성 결과를 구별해 기록한다.
- JSON 검사 전에 코드 울타리를 제거했다. 새 기본 검사는 원문 출력을 그대로 검사하고 계약 이탈을 실패로 남긴다.
- 한국어 글자 수와 영어 단어 수를 합쳐 길이를 판정했다. 새 출력 계약의 사용자용 길이는 문자 수, 생성 상한은 토큰 수로 구별한다.
- `pre-warming`을 공통 문맥과 대화 히스토리의 의미로 사용했다. 운영본은 문맥 구성과 모델 사전 로드·메모리 유지를 나누어 설명한다.
- 원본의 고객지원 봇 예시를 합성 문의 분류 서비스로 발전시켜, 여러 기법이 같은 과업에서 어떻게 작동하는지 확인한다.

### 02 · 추론 보조

- 저장된 셀 19 출력에 `SyntaxError: unterminated string literal`이 남아 있다. 원본 보존 파일의 정상 실행을 주장하지 않는다.
- `safe_execute_code`는 위험 문자열을 일부 확인한 뒤 `exec`를 호출하고, `safe_execute_calculation`은 모델 코드를 실행한다. 이 코드를 안전한 샌드박스로 소개하지 않는다.
- PAL의 “100% 정확” 같은 표현은 실행 코드와 문제 변환의 정확성을 보장하지 않는다. 운영본은 계산 결과의 검증과 코드 실행 격리 조건을 설명한다.
- “Ollama는 툴 호출 미지원”이라는 일반화는 현재 공식 기능과 맞지 않는다. 지원 모델·실제 도구 실행·프로그램 권한을 구별한다.
- 긴 내부 사고 내용을 출력하도록 유도하는 실습 대신, 사용한 근거·짧은 판단 이유·검토 가능한 결과를 요청한다.
- 복잡한 문제 분해와 후보 탐색은 참고 장표에서 원문 논문의 적용 범위와 함께 다룬다.

### 03 · 고급 통합

- 저장된 셀 16 출력에 `NameError: name 'ape_result' is not defined`가 있다. 셀 실행 순서에 의존하는 상태를 새 실습의 필수 경로에서 제거한다.
- `PromptVersionManager._evaluate_result`는 `expected`를 받지만 분류 정답과 비교하지 않고 JSON·길이·한글·키워드 존재에 점수를 준다. 새 실습은 기대 분류와 검토·우선순위를 명시적으로 비교한다.
- 원본의 “최종 검증”은 JSON 성공률과 모델 자체 confidence 평균으로 프로덕션 기준을 판정한다. 운영본은 자체 confidence를 정확도나 배포 승인으로 사용하지 않는다.
- 원본 버전 관리에서 전역 상태와 결과가 메모리에 남는다. 새 실습은 프롬프트 파일·버전·내용 해시·사례 해시·실행 설정·검사·결정 기록을 내보낸다.
- “팬아웃/팬인” 예시는 다중 관점을 순차 호출한다. 병렬 처리 성능을 검증한 결과로 소개하지 않고, 실제 실행 방식과 호출 수를 확인하도록 연결한다.
- 자동 프롬프트 탐색은 개발 사례와 별도 검토 사례의 분리, 평가 기준 고정과 사람의 채택 판단을 설명하는 참고 자료로 옮긴다.

### 04 · 운영 기법

- 모듈·클라이언트 초기화와 설치, 감정 분류, 필터, 복구가 하나의 큰 노트북에 결합되어 있다. 필수 수업은 서비스 실행·검사·기록의 작동 범위에 집중한다.
- 일부 파싱 경로는 오류를 `{"error": ...}` 객체로 반환하거나 분류 실패를 중립 감정으로 바꾼다. 운영본은 실패 원인과 미평가 항목을 명시해 성공과 섞지 않는다.
- 모든 예외를 동일하게 재시도하는 방식은 잘못된 입력과 일시적 연결 문제를 구별하기 어렵다. 현재 필수 실습은 제한된 실행 시간과 명시적 오류를 사용하고, 재시도·회로 차단·대체 경로는 후반 운영 주차로 연결한다.
- 감성 분석과 실제 고객의 요청 의도를 구별한다. 어조가 공손해도 담당 분류나 승인 내용이 잘못되면 실패라는 점을 사례로 확인한다.
- 정규식이나 프롬프트 하나가 모든 개인정보와 위험 표현을 막는다고 주장하지 않는다. 공개 실습에는 처음부터 합성 사례를 사용한다.

## 새 실습의 비교 설계

| 항목 | 설계 |
|---|---|
| 서비스 | PROMPT/02 · 고객 문의 분류와 상담 답변 초안 |
| 입력 | T01–T08 합성 문의, 기대 분류·우선순위·검토 여부 |
| v1 | 간단한 업무 지시 |
| v2 | 출력 형식과 업무 규칙 |
| v3 | v2 규칙 유지, 평가와 다른 예시 A/B/C 추가 |
| 출력 | category, priority, needs_review, reply |
| 검사 | 형식, 분류, 확정 약속, 검토·우선순위 |
| 보존 | 원본 응답, 오류, 내용 해시, 설정, 결과, 결정 |
| 외부 조치 | 환불 승인·주문 변경·실제 전송 없음 |

v1과 v2는 여러 명세 항목을 묶어 바꾼 설계안 비교다. 모든 차이를 단일 문구의 인과 효과라고 해석하지 않는다. v2와 v3는 업무 규칙을 유지하고 예시를 추가한다. 실제 모델 비교에서는 모델·생성 옵션·사례·평가 규칙을 함께 기록한다.

demo는 실제 모델 대신 **의도적으로 구성한 응답 묶음**을 재생한다. 따라서 “v3가 항상 더 정확하다”, “성능이 일정 비율 향상되었다”는 주장을 만들지 않는다. 프롬프트 편집의 실제 생성 효과는 선택 Ollama 실행으로 별도 확인한다.

Ollama 기본 태그는 `qwen3:4b-instruct`, 요청은 `think:false`, `temperature:0`, `seed:42`, `num_ctx:4096`, `num_predict:384`, `keep_alive:"30m"`이다. 형식 제약을 API에 추가하면 비교 변수가 달라지므로 기본 비교에서는 `format`을 사용하지 않는다. 온도와 seed 고정이 모든 장비에서 완전히 동일한 출력을 보장한다는 표현은 사용하지 않는다.

## 수업에서 남길 증거

1. 출력 계약과 변경 의도를 설명할 수 있는 프롬프트 파일
2. 동일 사례의 버전별 응답과 검사 결과
3. 형식·분류·약속·검토 가운데 실패 1건의 원문 근거
4. 선택 후보·남은 위험·추가 확인을 적은 결정 기록
5. 설정과 사례·프롬프트 식별값을 포함한 JSON 보고서

다음 3주차에서는 사례의 대표성, 라벨 합의, 실패 유형과 반복 평가를 넓힌다. 이번 8개 개발 사례의 통과를 전체 고객 분포의 성능 보증으로 확대하지 않는다.
