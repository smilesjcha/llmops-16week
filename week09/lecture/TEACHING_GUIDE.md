# 9주차 · 80쪽 초안과 100분 진행안

## 수업 목적

8주차 기획서의 요구사항 하나를 API(Application Programming Interface, 응용 프로그래밍 인터페이스)로 만들고 정상·실패·중단을 설명한다. 2025 보존본의 FastAPI·추론 최적화·캐시·부하 주제를 계승하되, API 계약과 복구를 우선하고 배포·보안·용량 계획의 상세는 이후 주차로 연결한다.

80쪽은 수업 설명과 복습 자료를 함께 담는다. 강의 중 모든 코드를 완독하지 않는다. 상세 배경·반례는 PPT 발표자 노트와 `lecture-notes.md`를 활용한다. 검증 리포트는 로컬 `output/validation/`에 둔다.

## 도입 질문

“한 명이 실행한 답변 함수가 잘 동작했는데 서비스 접속자가 늘면 무엇이 달라질까?”를 먼저 묻는다. 사용자의 입력 오류, 상류 지연, 브라우저 종료, 과부하를 각각 분리한다. 모두를 ‘LLM 오류’로 묶지 않는다.

13–16쪽에서 요청 모델과 출력 모델을 읽는다. 스키마 통과는 내용 정확성과 다르며,422는 입력 수정이 필요한 상태다.15쪽의 원문 없는 검증 오류는 개인정보가 예외 응답으로 복제되는 경로를 줄이는 예시다.

## 비동기와 용량의 설명

24쪽의30ms 수면4건은 동시 대기의 개념 설명이다. CPU/GPU 계산을4배 빠르게 한다는 뜻이 아니다. `async def` 안의 `time.sleep`·동기 HTTP 호출은 이벤트 루프를 막을 수 있다. 강좌는 CPython3.11을 기준으로 GIL을 설명하고 다른 버전 조건과 섞지 않는다.

29–30쪽의 질문은 “초당10건과 동시에10건은 같은가?”다. 응답이 길어지면 유입 빈도가 그대로여도 작업 점유가 늘 수 있다. 이번 앱은 대기열 없이 처리 한도를 넘으면503, 글로벌 토큰 버킷을 넘으면429를 반환한다. 이는 단일 프로세스의 실험 장치이며 인증된 사용자별 정책은 아니다.

32–35쪽에서 제한시간 이후 `active=0`을 확인한다. 코루틴 취소·HTTP 연결 단절·외부 GPU 작업 종료는 별개다. 자동 재시도는 구현하지 않았고 중복 실행·비용·횟수·전체 시간 예산을 검토한다.

## 캐시와 논문 읽기

37쪽의 세 캐시는 재사용 대상부터 다르다. 응답·검색·KV 캐시를 하나의 ‘빠르게 하는 기능’으로 소개하지 않는다.39–40쪽에서 권한이나 모델 버전이 누락된 재사용의 위험을 검토한다. 해시는 암호화가 아니고 캐시값은 답변을 보유한다.

43쪽의 콜드 캐시 중복은 의도적으로 남긴 반례다. 기본 구현이 진행 중 작업을 합치지 않음을 먼저 실행하고, 합치려면 대기자 취소·실패 공유·키별 메모리 한도를 어떻게 정할지 질문한다.

45–46쪽은 Kwon et al., SOSP2023의 원본 Figure5·4를 흑백 발췌했다. 블록 참조·스케줄러·캐시 관리자를 읽고 API 앱과 추론 엔진의 역할을 구분한다. 논문 성능 수치를 로컬 실습 성과로 전이하지 않는다. 상세 출처와 라이선스는 `assets/SOURCES.md`다.

## 스트리밍 설명

50–54쪽에서 `meta → delta → done`과 `meta → error`를 구분한다. 헤더 이후 실패는 HTTP200으로 남을 수 있어 `done`을 성공 기준에 포함한다. POST 본문은 브라우저 fetch로 보내고 기본 EventSource에 POST body를 넣는 방식은 사용하지 않는다.

Notebook04의 ASGITransport는 이벤트 형식·오류 계약을 검사한다. 도착 간격은 실제 TCP 검증 스크립트에서 별도로 확인한다. 고정 문장의 문자 조각이므로 TTFT(Time To First Token, 첫 토큰까지의 시간)나 모델 토큰/초를 실측했다고 말하지 않는다.

## 부하 결과 토론

Notebook05는 처리 용량2에서 동시성1·2·6을 비교한다. 캐시는 끄고 워밍업2건을 제외하며 실행별24건이다. 성공 응답만의 p50/p95, 전체 요청의 오류율, 성공 요청/s를 함께 읽는다. 빠른503이 전체 완료 처리량이나 평균을 좋아 보이게 만들 수 있다.

66쪽의 가상 사례는 평균10.9ms지만90%가 실패한다. 실제 결과는 기기·실행 시점·스케줄링에 따라 달라진다. 작은 표본의 p99나 폐쇄형 단기 시험으로 장기 서비스 목표를 보장하지 않는다.

## 프로젝트 리뷰

74쪽의 기능 요구사항·비기능 요구사항을 각 팀의 기획에 대응시킨다. 제출한 기획서를 다시 만드는 활동보다 최소 기능 하나의 정상·오류·중단 시험을 누적한다. 구현 전 목표값과 실측값을 구분한다.

선택 Ollama는 설치된 정확한 모델 태그·서버 상태·thinking 지원을 확인한다. 어댑터는 모의 HTTP 전송으로 검사했으며 실제 모델 속도·품질은 검증 범위가 아니다. 실제 제공자 스트리밍은 미지원임을 명시한다.

다음 주는 배포 구조·실행 관찰·복구다. 별도 필수 과제 기한·배점을 추정하지 않고 소속별 공지로 확정한다.
