# 3주차 강의안 · 프롬프트 평가와 오류 분류

2026.09.18 · 실시간 온라인 · 100분

차성재 · 무신사 Core AI PM × AI 대학원 겸임교수

## 수업의 질문

프롬프트를 바꾼 결과를 어떤 기준으로 통과·실패로 판정하고, 그 판단을 다음 실험과 프로젝트 기획서에 남길 것인가.

이번 주의 `EVAL/03`은 합성 회의 발췌와 교육용 고정 응답을 이용한다. 외부 모델·API 키·실제 회의록을 쓰지 않는다. 따라서 화면의 통과율은 실제 Large Language Model(LLM) 성능이 아니며, **평가 기준과 오류 기록의 흐름을 재현하는 수업용 결과**다.

## 완료 증거

1. 구조·핵심 사실·근거·실행 항목의 평가 기준을 설명한다.
2. 개발 사례(dev)와 확인 사례(test)의 사용 시점을 구분한다.
3. M02 또는 M03 한 건을 원문·출력·실패 기준·다음 확인으로 설명한다.
4. 후보·보류·제외 중 하나를 근거와 함께 JSON 보고서에 남긴다.

## 진행 원고

### 1. 시작 · 1–7장

2주차에는 같은 입력에서 프롬프트 버전을 비교했다. 3주차에는 “어느 버전이 좋아 보이는가”가 아니라 “어떤 결과를 어떤 기준으로 통과라고 말할 것인가”를 다룬다. 한 문장으로 답하게 한다.

> 결과가 좋다는 말 대신, 사례·기준·실패·다음 확인을 함께 말할 수 있어야 한다.

16주 과정은 전부 온라인이다. 4주차와 6주차 공휴일은 실시간 수업 대신 녹화 강의영상 업로드로 대체한다. 8주차는 중간고사와 실시간 수업 없이 기말 프로젝트 기획서의 온라인 제출·평가로 진행하고, 16주차에는 프로젝트 발표를 실시간 온라인으로 진행한다.

### 2. 평가 기준 · 8–22장

평가 대상은 모델 이름 하나가 아니라 입력, 프롬프트, 설정, 출력 검사까지 포함한 실행 단위다. 이 실습의 네 기준은 아래와 같다.

| 기준 | 질문 | 대표 실패 |
|---|---|---|
| 구조 | 약속한 네 섹션이 있는가 | v0.1의 한 문단 요약 |
| 핵심 사실 | 사례에서 정한 핵심 문구가 남았는가 | 담당·기한 등 앵커 누락 |
| 근거 | 원문에 없는 확정 사실을 추가하지 않았는가 | `검토 중`을 `승인 완료`로 표현 |
| 실행 항목 | 담당자·기한 또는 `미정`을 실행 항목 안에 적었는가 | M02의 미정 정보 누락 |

루브릭은 이번 업무와 합성 사례에 대한 판단 계약이다. 모든 한국어 회의록 품질이나 실제 서비스 안전성을 보장하지 않는다. 앵커 기반 검사는 동의어와 문맥을 놓칠 수 있으므로, 실제 프로젝트에서는 표본 검토와 새 사례를 추가한다.

개발 사례는 개선에 쓰고, 확인 사례는 선택 뒤에 별도로 본다. 확인 사례를 읽으며 프롬프트를 계속 바꾸면 그 사례는 독립적인 확인 근거가 아니게 된다.

### 3. 실습 준비 · 23–31장

`EVAL/03`은 합성 회의 발췌 6건과 고정 응답으로 구성한다. v0.1은 짧은 요약, v0.2는 구조화 회의록이다. 응답은 고정되어 있으므로 프롬프트 파일을 수정해도 Demo 결과는 바뀌지 않는다. 수업의 목적은 프롬프트 반응을 재는 일이 아니라 **평가와 기록의 순서**를 익히는 일이다.

서버 주소는 `http://127.0.0.1:8003`이며, 1주차 8000번·2주차 8002번 서버와 동시에 실행할 수 있다. 환경 문제 수강생은 화면을 보면서 평가 기준과 실패 기록부터 작성한다.

### 4. 실습 · 33–48장

1. `dev` 4건을 선택하고 두 버전을 평가한다.
2. v0.1에서 필수 섹션이 없어 구조 검사에 실패하는 이유를 확인한다.
3. M02에서 `미정`이 다음 단계에는 있어도 실행 항목에는 없어 `action_ok = false`가 되는 이유를 확인한다.
4. M03에서 원문의 `검토 중`이 출력의 `예산 승인 완료`가 되어 `evidence_ok = false`가 되는 이유를 확인한다.
5. `test` 2건으로 별도 평가한다.
6. v0.2를 즉시 채택하지 말고 `보류`로 기록한다. 근거에는 M02·M03 오류와 다음 확인 사례를 쓴다.
7. JSON 보고서를 저장한다.

Demo 수치의 정확한 해석: v0.1 dev `0/4`, v0.2 dev `2/4`, v0.1 test `0/2`, v0.2 test `2/2`는 이 저장소의 고정 응답 결과다. 작은 사례 수이므로 일반 성능, 사용자 만족, 배포 준비 완료로 해석하지 않는다.

### 5. 결과 해석과 다음 주 · 49–60장

합계 점수만으로 결정하지 않는다. 누락·왜곡·형식 실패는 서로 다른 대응을 요구한다. 특히 원문에 없는 확정 정보는 업무 위험과 연결될 수 있으므로, 같은 한 건이라도 사람 검토와 새 사례가 필요하다.

기획서에는 다음 네 줄을 누적한다.

1. 서비스에서 만들고 싶은 결과
2. 결과가 맞다고 볼 최소 기준
3. 대표 성공 사례와 실패 사례
4. 후보·보류·제외의 현재 판단과 다음 확인

다음 주에는 검색 증강 생성(Retrieval-Augmented Generation, RAG)의 근거와 인용을 다룬다. 검색 결과도 “찾았다”가 아니라 어떤 문서를 어떤 근거로 답변에 사용했는지 평가 대상으로 이어 간다.

5. JSON 보고서를 수업 종료 전 저장한다.
