# EVAL/03 · 평가 기준과 오류 분류

프롬프트 v0.1(짧은 요약)과 v0.2(구조화 회의록)를 동일한 합성 회의 발췌에 적용한 것으로 가정하고, **구조·핵심 사실·근거·실행 항목** 네 기준을 검사하는 3주차 실습이다. 모델을 호출하지 않고 준비된 응답을 평가하므로 모든 필수 실습은 오프라인에서 재현된다.

## 실행

```bash
.venv/bin/python -m uvicorn eval03.main:app --app-dir week03/lab --host 127.0.0.1 --port 8003
```

열기: <http://127.0.0.1:8003> · 상태: <http://127.0.0.1:8003/health> · API 문서: <http://127.0.0.1:8003/docs>

서버 터미널은 유지하고 새 터미널에서 아래를 실행한다.

```bash
PYTHONPATH=week03/lab .venv/bin/python -m eval03.smoke
PYTHONPATH=week03/lab .venv/bin/python -m pytest week03/lab/tests -q
.venv/bin/python -m ruff check week03
```

## 31분 필수 실습

| 시간 | 작업 | 확인할 증거 |
|---:|---|---|
| 0–4분 | `dev` 4건으로 두 버전 평가 | 같은 사례·같은 루브릭·서로 다른 프롬프트 |
| 4–12분 | v0.1과 v0.2 결과 행 열기 | 구조 실패와 통과를 구분 |
| 12–19분 | M02·M03 실패 상세 읽기 | 실행 항목의 미정 표기, 근거 없는 예산 승인 단정 |
| 19–25분 | `test` 2건으로 재평가 | 개발 사례와 확인 사례 분리 |
| 25–31분 | 후보 결정 기록·JSON 내보내기 | 버전·근거·다음 확인을 함께 기록 |

## 평가 기준

| 기준 | 코드 필드 | 이번 합성 사례에서 확인하는 것 |
|---|---|---|
| 구조 | `structure_ok` | 결정 사항·실행 항목·위험/확인 필요·다음 단계 네 섹션 |
| 핵심 사실 | `coverage_ok` | 사례별로 정한 앵커 문구 누락 여부 |
| 근거 | `evidence_ok` | 원문에 없는 확정·승인·보장 표현 추가 여부 |
| 실행 항목 | `action_ok` | 실행 항목 섹션에 담당자·완료일 또는 `미정` 표기 |
| 전체 통과 | `overall_ok` | 네 검사를 모두 통과했는지 |

검사는 제한된 루브릭이다. 모든 한국어 회의록의 품질, 사실성, 보안, 업무 정책을 완전하게 판단하지 않는다. 특히 문자열 앵커 검사는 동의어와 문맥을 놓칠 수 있으므로, 후보를 실제 서비스에 적용할 때는 표본 검토와 새 사례 평가를 추가해야 한다.

## Demo 결과의 올바른 해석

- `dev`: 프롬프트와 평가 기준을 함께 다듬을 수 있는 개발 사례 4건
- `test`: 선택 후에만 확인하는 별도 사례 2건
- v0.1의 dev 전체 통과 `0/4`, v0.2의 dev 전체 통과 `2/4`는 **이 저장소의 고정 응답 결과**다.
- v0.2의 test 전체 통과 `2/2`도 사례 수가 작고 고정되어 있어 운영 채택 근거가 아니다.
- 프롬프트 파일을 수정해도 Demo 응답은 바뀌지 않는다. 달라지는 것은 프롬프트 원문·해시뿐이다.
- JSON 보고서는 서버 메모리가 초기화되기 전에 내려받는다. 실제 배포나 외부 전송은 일어나지 않는다.
