# 11주차 강의 노트

## 01. LLM 서비스의 품질 검증

표지의 HOLD는 꾸민 수치가 아니라 이번 실습의 실제 결과다. 왜 검색 성능이 좋아졌는데도 배포를 보류하는지 수업 전체에서 설명한다. Core AI PM은 핵심 인공지능 제품 관리 역할이다.


## 02. 하나의 점수로 부족한 판단

가상 정책 데이터의 실제 TF-IDF 실행이다. LLM 답변 생성 정확도가 아니다. 답변 가능한 test 16개, 답변 불가 8개를 서로 다른 분모로 사용한다. 어떤 수치를 보면 후보를 채택하고 싶은지 먼저 묻는다.


## 03. 수업의 세 가지 산출물

오늘 목표는 도구 이름을 많이 외우는 것이 아니라 평가 결과로 한 번의 의사결정을 설명하는 것이다.


## 04. 16주 과정의 현재 위치

6주차는 녹화영상과 신규 과제도 없었다. 8주차는 중간고사 없이 제출물 평가였으며 10월22일23:59 마감이었다. 16주차는 온라인 실시간 발표다. 오늘은 11주차 평가 데이터를 프로젝트 증거로 추가한다.


## 05. 100분 수업의 진행

76쪽 전체를 같은 속도로 읽지 않는다. 계산 심화와 참고 장표는 필요할 때 열고 핵심 셀 위주로 실행한다. 수업 전 requirements 설치를 완료하면 시간을 확보할 수 있다.


## 06. 실행 관찰과 품질 평가

HTTP 200과 낮은 지연은 중요한 운영 신호지만 정답이라는 증거가 아니다. OpenTelemetry와 Prometheus는 오늘 품질 지표를 대신 채점하는 도구가 아니다.


## 07. 오프라인 평가와 온라인 실험

오프라인을 통과하면 즉시 전체 사용자에게 배포하는 것이 아니다. 온라인에서 실패 범위를 제한하며 검증해야 한다.


## 08. 평가 파이프라인의 구조

각 단계의 산출물이 다음 단계 입력이 된다. 좋은 보고서에도 데이터 출처나 버전이 없으면 재현이 어렵다.


## 09. 평가 단위의 결정

이번 검색 지표는 문서 ID 기준이다. 실제 프로젝트에서 청크를 사용하면 정답 단위와 중복 처리 규칙을 다시 정의한다.


## 10. 평가 기준의 지도

같은 지표 이름도 입력과 분모가 다르면 비교할 수 없다. 이 수업의 검색 점수를 범용 LLM 성능으로 확대 해석하지 않는다.


## 11. 평가 데이터

앞 구간의 결과를 한 문장으로 연결하고 이번 구간에서 학생이 직접 확인할 산출물을 안내한다.


## 12. 오늘의 서비스 사례

실제 무신사 정책이나 법률 안내가 아니다. 학습을 위해 만든 가상 쇼핑 정책임을 분명히 말한다. 사용자 질문은 한 문장이지만 필요한 근거는 여러 개일 수 있다.


## 13. 정답처럼 보이는 구버전 문서

잘못된 답이 반드시 모델 환각은 아니다. 잘못된 버전의 검색 근거에서 출발할 수 있다. status와 version을 색인 계약에 포함한다.


## 14. 질문 한 건의 데이터 계약

reference는 검토용이다. 검색기에 넣으면 정답을 입력으로 제공하는 오류다. gold 문서가 실제 존재하는지 자동 검증한다.


## 15. 정답 근거의 판정

문자열 일치만으로 의미를 판정하면 같은 뜻의 답을 오답 처리하거나 조건이 다른 답을 통과시킬 수 있다.


## 16. 복수 근거 질문의 성공 조건

초기 AS-IS 실습의 단일 정답에서는 Hit와 Recall이 같아 차이를 보기 어려웠다. 복수 근거로 지표의 의미를 구분한다.


## 17. 답변할 수 없는 질문

문서에 답이 없으면 검색기가 비슷한 문서를 찾아도 정답 근거가 아니다. 이 실습은 기권 정책만 검사하며 실제 외부 조회를 수행하지 않는다.


## 18. 개발 세트와 평가 세트의 분리

같은 의도의 정중한 질문과 구어체 질문은 같은 split에 둔다. 문서 집합은 공유하며, 새로운 도메인 적응 실험으로 주장하지 않는다.

출처: https://scikit-learn.org/1.7/common_pitfalls.html#data-leakage

## 19. 누수의 대표적인 경로

코드에서는 group이 dev/test에 동시에 나타나면 예외를 발생시킨다. 실제 운영은 사용자나 대화 단위 의존성도 확인해야 한다.

출처: https://scikit-learn.org/1.7/common_pitfalls.html#data-leakage

## 20. 합성 평가 데이터의 제작 과정

이번 사례는 교수 작성 합성 데이터다. LLM을 자동 호출해 생성한 데이터가 아니다. 실제 모델 생성으로 확장하더라도 검수 단계는 생략하지 않는다.


## 21. 연구 사례: ARES의 평가 구조

ARES는 합성 데이터를 활용해 평가 모델을 학습하고 사람 주석과 예측 기반 추론으로 시스템 평가를 보정한다. 우리 실습은 ARES를 실행한 재현이 아니다. 원본 연구의 역할 분리를 참고한다.

출처: https://arxiv.org/html/2311.09476v2

## 22. 연구 구조와 수업 실습의 범위

문서 없는 질문을 모두 버릴 필요는 없다. 답변 불가 유형으로 정확하게 라벨링하면 중요한 위험 평가 데이터가 된다.

## 35. 평균 역순위: MRR

여기서는 k 안의 첫 정답만 계산하므로 MRR@k라고 표기한다. 여러 질문의 reciprocal rank를 평균낸다.

규칙 기반 검증은 싸고 빠른 경보지만 의미 전체를 평가하지 못한다. 반대로 LLM 판정도 오류가 있으므로 서로 다른 검사를 조합한다.


## 58. 평가자와 참고 판정의 불일치

행은 교수 작성 참고 판정, 열은 교수 작성 예시 평가자 출력이다. 조건 확대·근거 누락·다른 표기의 오판을 한 건씩 읽는다. 합성 예시 수치를 실측 모델 성능으로 발표하지 않는다.


## 59. 위치 편향과 길이 편향

MT-Bench 연구는 LLM 평가자의 위치·장황함·자기 선호 등의 한계를 분석했다. 모든 모델과 설정에서 같은 정도로 나타난다고 말하지 않는다.

## 60. 실제 LLM 평가로 확장할 조건

LLM judge를 도입하면 결과를 정답으로 고정하지 말고 검증해야 한다. 평가자 모델을 바꾸면 같은 시스템의 점수가 바뀔 수 있다.


## 61. 실습 05: 평가자 오류 읽기

fixture는 실제 LLM 응답이 아니라 작성 예시임을 다시 확인한다. 숫자를 높이는 것보다 어떤 오판이 위험한지 설명하게 한다.


## 62. 보고서와 의사결정

앞 구간의 결과를 한 문장으로 연결하고 이번 구간에서 학생이 직접 확인할 산출물을 안내한다.


## 63. 같은 질문의 짝 비교

bootstrap은 관측 그룹을 다시 뽑는 계산이다. 새로운 실제 사용자 분포를 생성하는 것은 아니다. 여기서는 그룹 평균에 같은 가중치를 준다.


## 64. 개선 폭의 불확실성

작은 표본의 percentile bootstrap 구간이다. 0 포함 여부만으로 사업 의사결정을 끝내지 않는다. 데이터 대표성과 중요한 실패 유형도 검토한다. 이 결과는 ARES의 PPI가 아니다.


## 65. 배포 전 검증 조건의 결과

결론은 HOLD다. CI가 개선 방향을 지지하더라도 사용성과 답변 불가 질문 처리의 기준을 충족하지 못한다. 통과 수를 평균내어 실패 조건을 상쇄하지 않는다.


## 66. 평가 보고서의 실제 화면

sample/report.html로 즉시 시연할 수 있고 Notebook06이나 CLI로 재생성할 수 있다. 보고서의 수치는 LLM 생성 정확도가 아니다.


## 67. 실습 06: 보고서 재생성과 확인

VS Code 탐색기에서 report.html을 브라우저로 연다. 서버가 필요 없다. HTML은 결과 데이터가 내장되어 오프라인으로 열린다.


## 68. 지속적 통합에서의 평가 연결

CLI는 HOLD일 때 종료 코드2를 반환한다. 설치 오류가 아니라 의도한 차단이다. 기본 명령은 학습을 위해 보고서를 만들고0으로 종료한다. REVIEW도 자동 배포를 의미하지 않는다.


## 69. 프로젝트에 추가할 평가 근거

2pager·PRD·PPT에 모든 코드를 넣지 않는다. 주장과 근거, 선택 이유를 짧게 쓰고 상세 보고서를 연결한다. 여러 프로젝트도 각자의 검증 근거를 제시한다.


## 70. 한 페이지 평가 기록의 구조

제안서의 두괄식 원칙을 평가 보고서에도 적용한다. 개선 과정의 일지를 길게 붙이지 않고 현재 판단을 먼저 설명한다.


## 71. 오프라인 통과 이후의 확인

오늘 기본 실습의 HOLD 후보를 실제 사용자에게 배포하라는 안내가 아니다. 일반적인 다음 검증 단계를 정리한다.
