## 02. 16주 과정의 현재 위치

## 04. LLM 서비스와 평가 지점

### 핵심 메시지

검색·생성·응답 처리의 실패를 나누어 봐야 원인을 찾을 수 있습니다.

### 설명 예시

RAG는 Retrieval-Augmented Generation, 검색 증강 생성입니다. 먼저 문서를 찾고, 그 근거를 모델에 전달해 답변을 만듭니다. 원문이 오래됐을 수도, 검색이 놓쳤을 수도, 모델이 조건을 빼먹었을 수도 있습니다. 결과 한 문장만 봐서는 세 원인을 구분하기 어렵습니다.

### 화면 짚기

흐름 보기로 원문·색인 → 질문·검색 → 생성·응답 → 평가 기록 순서 강조.

### 확인 질문

교환 비용이 틀리면 가장 먼저 어디를 확인할까요?

### 기대 답변

실제로 검색된 문서와 모델 입력을 확인한 뒤 생성의 사용 오류를 구분합니다.

### 오해 방지

자체 구성한 참조 구조입니다. 모든 서비스의 단일 표준이나 모든 보안 기능의 구현은 아닙니다.

### 다음 연결

## 05. 배포 전 평가 아키텍처

### 핵심 메시지

### 오해 방지

## 06. Trace와 Span의 역할

### 핵심 메시지

Trace는 요청 전체, Span은 그 안의 작업 한 단계입니다.

### 설명 예시

상담 한 건의 처리 기록 전체를 Trace라고 생각하면 됩니다. 검색, 답변 생성, 코드 검사처럼 시작과 끝이 있는 작업은 각각 Span으로 나눕니다. Langfuse는 이런 작업을 Observation으로 표현하고 generation·retriever 같은 유형도 붙입니다. 오늘은 요청 하나 안에서 무엇이 일어났는지 연결해서 읽는 연습입니다.

### 화면 짚기

트리의 맨 위와 네 자식 행을 나누어 짚기. 생성과 모델 평가 모두 모델 호출임을 예고.

### 확인 질문

답변을 한 번 했는데 generation이 두 개일 수 있을까요?

### 기대 답변

답변을 생성한 호출과 그 답변을 평가한 호출이 따로 있기 때문입니다.

### 오해 방지

Span은 토큰 한 개나 모든 로그 한 줄을 뜻하지 않습니다. 07–08 JSONL과 09–10 SDK 전송도 구분합니다.

### 다음 연결

추적할 사례의 성공 조건을 먼저 정하겠습니다.

출처: https://opentelemetry.io/docs/concepts/signals/traces/

## 07. 서비스 사례와 성공 조건

### 핵심 메시지

사용자 질문을 판정 가능한 성공 조건으로 나눕니다.

### 설명 예시

“사이즈가 작아요”라는 질문에는 교환 가능 기간과 비용이 함께 들어 있습니다. “교환 가능합니다”라고만 답하면 친절하지만 충분하지 않습니다. 기간, 재고 조건, 배송비처럼 반드시 포함할 정보를 적어야 검사가 가능합니다.

### 화면 짚기

사용자 요구·필요 근거·실패 영향을 읽고 D03과 D04 연결.

### 확인 질문

이 답변에서 하나만 빠져도 문제가 될 정보는 무엇인가요?

### 기대 답변

7일 이내 신청, 재고 조건, 단순 변심 왕복 배송비 6000원입니다.

### 오해 방지

실제 기업 정책이 아니라 수업의 가상 정책입니다.

### 다음 연결

## 08. 질문과 참고 기준의 구조

### 핵심 메시지

평가 문항에는 질문뿐 아니라 판정 근거가 필요합니다.

### 설명 예시

질문 ID는 결과를 다시 찾기 위한 주소이고, gold_ids는 필요한 근거 문서입니다. answerable은 현재 자료로 답할 수 있는지를, reference는 검토할 내용을 담습니다. 정답 문장 하나를 외우게 하는 대신 어떤 사실과 조건을 충족해야 하는지 기록합니다.

### 화면 짚기

Q03a의 gold_ids 두 개와 reference를 함께 읽기.

### 확인 질문

gold_ids와 reference는 같은 정보인가요?

### 기대 답변

전자는 근거 문서 식별자, 후자는 답변을 검토할 참고 내용입니다.

### 오해 방지

모델에 reference를 입력하거나 존재하지 않는 문서를 정답으로 지정하지 않습니다.

### 다음 연결

## 09. 문서 버전과 정답 근거

### 핵심 메시지

문서 유사도보다 먼저 유효한 정책 버전을 확인합니다.

### 설명 예시

과거 정책도 질문과 아주 비슷해서 검색될 수 있습니다. “14일”이라는 표현을 정확히 복사했더라도 현재 정책이 7일이면 서비스 답변은 틀립니다. 이때는 프롬프트를 먼저 고치기보다 문서 상태와 색인 대상을 확인하는 것이 맞습니다.

### 화면 짚기

D01/D19, D02/D20의 현재·폐기 상태를 쌍으로 비교.

### 확인 질문

모델이 근거를 충실히 따랐는데도 틀릴 수 있을까요?

### 기대 답변

근거 자체가 폐기된 버전이면 가능합니다.

### 오해 방지

버전 필터와 접근 권한 필터는 목적이 다릅니다. 이 실습은 버전 필터를 구현했습니다.

### 다음 연결

## 10. 답변할 수 없는 질문

### 핵심 메시지

답변할 수 없는 질문도 평가 세트의 중요한 구성입니다.

### 설명 예시

재고와 배송 기사 위치는 실시간 조회가 필요한 정보입니다. 정책 문서 검색을 잘한다고 현재 상태까지 알게 되지는 않습니다. 평가에는 이런 경계 질문을 넣고, 추측 대신 확인 불가 안내나 조회 경로 연결이 적절한지 살펴봅니다.

### 화면 짚기

정책 범위 밖·실시간 상태·개별 상품 정보의 차이.

### 확인 질문

“재고가 없다”와 “재고를 확인할 수 없다”는 같은 답인가요?

### 기대 답변

전자는 상태를 단정하고, 후자는 서비스가 가진 정보의 한계를 설명합니다.

### 오해 방지

실시간 재고 API는 연결하지 않았습니다.

### 다음 연결

## 11. 개발 세트와 평가 세트의 분리

### 핵심 메시지

표현만 다른 같은 의도는 같은 데이터 묶음에 둡니다.

### 설명 예시

“반품비 얼마예요?”와 “반품 배송비가 궁금합니다”는 문장이 달라도 같은 의도입니다. 하나로 규칙을 조정하고 다른 하나로 검증하면 새 문제를 푼 것처럼 보일 수 있습니다. 개발 세트는 설정 선택에, 고정 평가 세트는 선택한 설정의 결과 관찰에 사용합니다.

### 화면 짚기

각 세트 24문항·12개 의도와 서로 다른 의도 그룹 표시.

### 확인 질문

문장 문자열만 중복 제거하면 누수를 막을 수 있을까요?

### 기대 답변

같은 의도·대화·고객 등 서로 의존하는 사례도 함께 분리해야 합니다.

### 오해 방지

여기서는 문서 집합은 공유하고 질문의 의도 그룹을 분리합니다.

## 13. 단어 검색과 문자 검색

### 핵심 메시지

단순한 검색기부터 비교해야 변경의 효과를 설명할 수 있습니다.

### 설명 예시

TF-IDF는 문서 안의 단어 빈도와 문서 집합에서의 희소성을 이용합니다. 단어 검색은 단어 경계에, 문자 검색은 부분 문자열에 반응합니다. 한국어 어미나 띄어쓰기 변화에서 결과가 달라지는 이유를 직접 읽기 쉬운 기준선입니다.

### 화면 짚기

단어 1–2그램과 문자 2–4그램의 특징·한계 비교.

### 확인 질문

문자 검색은 의미를 이해하는 임베딩 모델인가요?

### 기대 답변

아닙니다. 이 실습은 둘 다 어휘 기반 특징을 비교합니다.

### 오해 방지

모든 질문에서 문자 검색이 우월하다는 결론은 내리지 않습니다.

저장된 예시에서 A와 B는 구조 검사 75%, C는 100%입니다. B에는 답변 불가 질문을 수락한 사례가 남아 HOLD, C는 자동 조건을 통과해 REVIEW입니다. 오늘 학생 실행에서는 결과가 달라질 수 있으니 출력된 이유를 읽어야 합니다. REVIEW를 배포 완료로 발표하면 안 됩니다.

### 화면 짚기

각 버전의 계약 통과율(structural_pass), 잘못된 수락(false_accept), 최종 결정과 분모 4를 함께 확인.

### 확인 질문

C의 100%를 서비스 정확도라고 부르면 왜 잘못일까요?

### 기대 답변

네 개의 계약 검사 결과이며 의미 품질이나 다양한 실제 사용자를 대표하지 않기 때문입니다.

### 오해 방지

이 수치는 저장된 실행 예시입니다. 속도와 모델 판정은 환경에 따라 달라질 수 있습니다.

### 다음 연결

HOLD와 REVIEW를 나누는 조건을 코드 수준에서 보겠습니다.

## 53. 배포 전 자동 차단의 조건

### 핵심 메시지

### 설명 예시

### 화면 짚기

### 확인 질문

### 기대 답변

### 오해 방지
