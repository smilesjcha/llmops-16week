# 기말 프로젝트 기획서 가이드

> 8주차 온라인 제출·평가 · 상시 교수 설계 리뷰 · 기말 프로젝트 포트폴리오

## 제출 목적

별도의 중간고사는 시행하지 않는다. **8주차에는 실시간 온라인 강의 없이 기말 프로젝트 기획서 0.1을 온라인으로 별도 제출하고, 제출물로 평가를 진행**한다. 1–7주차에 만든 문제 정의, 실행 증거, 데이터 검토, 기술 선택과 평가 계획을 하나의 문서로 통합하고, 매주 교수 설계 리뷰에서 확인한 가정과 학생의 결정을 수정 이력으로 남긴다.

실제 작성은 [기말 프로젝트 기획서 템플릿](02_기말프로젝트_기획서_템플릿.md)에서 시작한다. 빠른 합의가 필요하면 [2페이지 제안서](web/project-proposal-2pager.html)를 먼저 작성하고, 세부 요구사항은 [제품 요구사항 문서(Product Requirements Document, PRD)](web/project-prd.html)로 확장한다.

좋은 기획서는 완성된 답을 가장하는 문서가 아니다. 무엇을 알고 있고, 무엇을 아직 모르며, 어떤 증거로 다음 결정을 내릴지를 명확히 하는 문서다.

## 제출 묶음

1. 기말 프로젝트 기획서 본문
2. 대표 입력과 기대 출력 예시
3. 기준선 실행 결과 또는 최소 프로토타입
4. 초기 평가표와 대표 실패 예시
5. 교수에게 확인할 우선 질문 3개 이내
6. 교수 설계 리뷰의 결정 기록과 후속 수정 계획

8주차에는 실시간 수업이나 시험을 진행하지 않는다. 제출일, 제출 경로, 파일 형식, 분량, 팀 구성과 배점은 학습관리시스템(Learning Management System, LMS)의 해당 학기 공지를 따른다.

## 권장 목차

### 1. 프로젝트 한 줄 정의

- 대상 사용자
- 해결할 업무 또는 의사결정
- 제공할 핵심 출력
- 기대하는 변화

형식 예시:

> `[대상 사용자]`가 `[현재의 어려움]`을 해결하도록 `[입력]`을 받아 `[검증 가능한 출력]`을 제공하는 서비스

### 2. 사용자와 문제 증거

- 핵심 사용자와 사용 맥락
- 현재 절차와 불편
- 이 문제가 실제라는 근거
- 인공지능 없이 해결하는 기준선
- 프로젝트에서 지원하지 않을 범위

### 3. 대표 입력과 출력 계약

- 대표 입력 3건 이상
- 기대 출력의 필드, 형식, 길이와 금지 조건
- 잘못된 입력과 오류 처리
- 사람이 검토하거나 승인해야 하는 지점

### 4. 데이터·권한·개인정보 경계

- 데이터 출처와 사용 권한
- 갱신 주기와 최신성
- 개인 식별 정보(Personally Identifiable Information, PII) 처리
- 저장·보존·삭제 기준
- 학습, 검색, 평가 데이터의 구분

### 5. 기준선과 기술 대안

- 규칙, 검색, 기존 모델 등 가장 단순한 기준선
- 프롬프트, 검색 증강 생성(Retrieval-Augmented Generation, RAG), 도구 호출, 모델 라우팅, 미세조정 후보
- 각 대안의 기대 효과, 비용, 가역성과 위험
- 선택한 접근과 선택하지 않은 접근의 이유

### 6. 평가 기준과 중단 조건

- 업무 품질: 사실성, 근거 연결, 형식, 누락, 유용성
- 운영 품질: 지연시간, 비용, 오류율, 재현성
- 안전성: 개인정보, 권한, 프롬프트 주입, 부적절한 행동
- 성공 조건, 실패 조건, 프로젝트 범위 축소 또는 중단 조건
- 자동 평가와 사람 평가의 역할

### 7. 시스템 구성과 개발환경

- 사용자 화면(User Interface, UI), 응용 프로그래밍 인터페이스(Application Programming Interface, API), 모델·도구, 저장소의 역할
- Python과 패키지 버전
- 실행·테스트·배포 경로
- 로그와 실행 추적(trace) 스키마
- 장애·시간 초과·외부 서비스 실패의 복구 경로

### 8. 9–15주차 실행 계획

- 주차별 기능과 검증 질문
- 담당자와 의존 관계
- 완료 조건
- 가장 큰 위험과 대체 경로
- 15주차 통합 점검과 시연 복구 계획

### 9. 현재 한계와 위험

- 아직 확인하지 못한 가정
- 데이터와 평가의 편향
- 비용·성능·일정의 trade-off
- 법적·윤리적·운영적 경계
- 사용자에게 명시할 한계

## 교수 질의응답 준비

질문은 넓은 조언 요청보다 **결정을 위한 선택지와 증거**가 있을 때 유용하다.

좋은 질문의 구조:

1. 현재 결정: 지금 선택하려는 것
2. 근거: 실행 결과, 사용자 자료, 데이터 또는 제약
3. 대안: 비교 중인 2–3개 선택지
4. 우려: 틀렸을 때 생길 가장 큰 위험
5. 요청: 교수에게 확인받고 싶은 판단

예시:

> 50개의 합성 질의에서 단순 검색보다 재순위 방식의 근거 포함률이 높았지만 95번째 백분위 지연시간이 증가했습니다. 현재는 정확도 우선 사용자를 대상으로 재순위를 선택하려 합니다. 제출 기획서에서 이 선택을 유지하려면 어떤 추가 실패 사례와 비용 근거가 필요할까요?

## 검토표

| 영역 | 확인 질문 | 최소 근거 |
|---|---|---|
| 문제·사용자 | 누구의 어떤 결정을 지원하는가 | 사용자 시나리오, 현재 절차 |
| 데이터·권한 | 사용할 수 있는 데이터인가 | 출처, 권한, 민감정보 정책 |
| 기술·대안 | 왜 이 접근을 선택했는가 | 기준선과 대안 비교 |
| 평가·위험 | 성공과 실패를 어떻게 판단하는가 | 평가표, 대표 실패, 복구 계획 |
| 실행·수정 | 9–15주차에 구현 가능한가 | 일정, 담당, 질의응답, 수정 이력 |

## 포트폴리오 정리 기준

최종 포트폴리오는 결과 화면만 보여주는 자료가 아니라 **판단이 개선된 과정**을 보여준다.

- 문제 정의의 변화
- 기준선과 선택한 기술
- 실패한 실험과 배운 점
- 교수 질의응답 전후의 결정 변화
- 품질·지연시간·비용·안전성의 실제 증거
- 현재 한계와 다음 버전

내부 데이터, 실제 고객 원문, 접근 토큰, 응용 프로그래밍 인터페이스 키(Application Programming Interface key, API key), 개인 연락처는 제출본과 공개 포트폴리오에서 제거한다.
